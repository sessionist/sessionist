# fixtures/ — the spec corpus

*Everything in this directory is MIT-licensed like the rest of the repository
(see the root `LICENSE`), so that any tool may test against this corpus.*

These are real OTLP wire bytes, but their origin is the specification, not a
framework. `spec/<scenario>/` is generated by `tools/spec-emitter` from the
OpenTelemetry GenAI semantic conventions at the commit pinned in
`tools/spec-emitter/schema/SOURCE.md`: each scenario exercises one feature of
the conventions, is emitted through the real OTel JS SDK and the official OTLP
exporters with deterministic ids and timestamps, and every content document on
a span was validated against the spec's own JSON schemas before export. The
corpus is reproducible byte for byte:

```sh
npm run fixtures     # regenerates spec/ and derives malformed/
```

The scenario list in `tools/spec-emitter/scenarios.ts` is the executable
definition of what "current generation" means for this sink. The test suite
asserts that the set of directories here equals that list.

## Layout and naming

```
fixtures/spec/<scenario>/
  meta.json            # scenario, description, spec repository + commit,
                       # encoding, SDK versions, batch count
  batches/
    NNNN.<signal>.<enc>  # request body VERBATIM as the exporter sent it
    NNNN.headers.json    # {"path": ..., "headers": {lowercased, verbatim}}
```

- `NNNN` — arrival counter at the capture sink, starting `0001`.
- `<signal>` — `traces` or `logs` from the POST path.
- `<enc>` — `pb` if the Content-Type contained `x-protobuf`, else `json`.

## Scenarios

| Scenario | Exercises |
|---|---|
| `agent-tool-loop` | `invoke_agent` bracket; two `chat` spans; one `execute_tool` linked to the model's `tool_call` part by `gen_ai.tool.call.id`; content on span attributes; system instructions; conversation id; usage; protobuf |
| `agent-tool-loop-json` | The same run as OTLP/JSON; must read identically |
| `content-as-log-record` | Metadata-only `chat` spans plus `gen_ai.client.inference.operation.details` log records carrying the messages |
| `error-path` | Error status on a tool call, a model call with an `exception` event, and the bracket |
| `no-conversation-id` | Two runs with no conversation or session id: the same-service time window |
| `explicit-session-id` | `session.id` present, conversation id absent |
| `subagent` | A child `invoke_agent` under the outer one |
| `other-operations` | `embeddings`, `text_completion`, `generate_content` (model calls); `create_agent`, `plan`, and one unknown name (plain spans) |
| `passthrough-mixed` | HTTP and database spans interleaved with convention spans in one trace |
| `large-payload` | A message array over the 32 KB blob threshold |
| `content-by-reference` | `gen_ai.*_ref` URIs with no inline content |
| `workflow-and-plan` | `invoke_workflow` bracket containing a `plan` span and an agent |
| `retrieval` | A `retrieval` span with query, `top_k`, and documents |
| `mcp-tool-call` | The spec's MCP example: client and server `tools/call` spans as tool calls, nested, never deduplicated |
| `mcp-session` | `initialize`, `tools/list`, `resources/read`: passthrough under the agent |
| `agent-transfer` | `execute_tool` with `gen_ai.transfer.*`: a `handoff`, then the target agent |
| `skills` | `load_skill` and `read_skill_resource` tool calls with `gen_ai.skill.name` |
| `fetch-response` | `fetch_response`: a model call with output only |
| `memory-operations` | Memory operations as plain spans with attributes |
| `exception-log-event` | `gen_ai.client.operation.exception` log record as an error event |
| `evaluation-event` | `gen_ai.evaluation.result` log record preserved, no verdict adopted |
| `tool-definitions-and-compaction` | `gen_ai.tool.definitions` into the payload; `gen_ai.conversation.compacted` preserved |

`malformed/` holds two mechanical derivatives, each with a `meta.json` naming
its source and mutation: `truncated-protobuf` (the receiver must 400 it and
keep serving) and `unrecognized-operation-json` (valid OTLP/JSON with operation
names outside the convention; must render as plain spans, never crash).

## What is not here

Recordings from frameworks. A batch recorded from eve, Mastra, or any other
framework is evidence about that framework, not a test of this sink, and the
sink is never changed to accommodate one. If a framework emits something the
conventions do not define, the right place for that is an issue on the
framework. The conventions repository runs its own conformance program with
per-library reports; this corpus does not duplicate it.

## Changing the corpus

- A new convention feature: add a scenario in `tools/spec-emitter/scenarios.ts`,
  run `npm run fixtures`, state the expected reading in
  `tests/normalize.test.ts`, refresh snapshots.
- A new spec commit: see `tools/spec-emitter/schema/SOURCE.md`; re-pinning is a
  deliberate change made in its own commit.
- Never edit recorded bytes by hand, and never hand-assemble OTLP; the SDK
  encodes.
